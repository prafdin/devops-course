\section{Цель документа}

Настоящий документ описывает общие правила, требования и процесс выполнения и сдачи лабораторных работ по курсу DevOps. Соблюдение этих правил обязательно для участников курса.

\section{Требования к обучающемуся для выполнения лабораторных работ}
Для успешного выполнения лабораторных работ обучающемуся необходимо иметь теоретические и практические навыки в следующих областях:
\begin{itemize}
    \item базовые навыки работы в UNIX-подобных операционных системах: понимание структуры файловой системы, процессов и прав доступа;
    \item навыки работы в командной строке: выполнение команд, работа с файлами и каталогами;
    \item основы компьютерных сетей: понимание принципов взаимодействия узлов в сети, назначение IP-адресов, принципы работы протокола HTTP;
    \item базовое понимание архитектуры клиент-серверных приложений.
\end{itemize}

\section{Требования к техническому обеспечению}
Для выполнения лабораторных работ обучающемуся необходимо наличие:
\begin{itemize}
    \item устройство под управлением операционной системы семейства UNIX либо возможность использования виртуальной машины под управлением данной операционной системы;
    \item стабильное подключение к сети Интернет;
    \item учетная запись в github.com.
\end{itemize}

\section{Организационные требования курса}

Перед началом выполнения лабораторных работ обучающемуся необходимо выполнить следующие организационные действия:
\begin{enumerate}
    \item выбрать приложение, используемое для выполнения лабораторных работ;
    \item выполнить создание копии (fork) исходного репозитория в личное пространство GitHub;
    \item создать pull request в исходный репозиторий для автоматических проверок;
    \item предоставить права доступа сервисному боту в созданном репозитории.
\end{enumerate}

\subsection{Выбор приложения для лабораторной работы}
Для выполнения лабораторных работ в данном курсе обучающемуся предлагается выбрать одно из приложений, предоставленных для работы.
Ознакомиться с приложениями можно по следующим ссылкам:
\begin{itemize}
    \item \textbf{Статический сайт:} \href{https://github.com/prafdin/website-example}
    \item \textbf{C\# приложение:} \href{https://github.com/danlla/Csharp-example}{danlla/Csharp-example}
    \item \textbf{Python веб приложение:} \href{https://github.com/prafdin/catty-reminders-app.git}{prafdin/catty-reminders-app}
\end{itemize}
В случае использования собственного приложения, которое не входит в предложенный список, необходимо согласовать его с преподавателем. При этом учитывайте, что:
\begin{itemize}
    \item автоматические проверки для собственного приложения применяться не будут;
    \item при сдаче лабораторных работ необходимо продемонстрировать работоспособность приложения преподавателю.
\end{itemize}

\subsection{Регистрация в репозитории для автоматических проверок}
Для сдачи лабораторных работ с применением автоматических проверок необходимо создать pull request в исходный
репозиторий \href{https://github.com/prafdin/devops-course-labs}{prafdin/devops-course-labs}.

В pull request необходимо добавить новый блок данных в файл params.json в список users.
В новый блок необходимо внести следующую информацию:
\begin{itemize}
    \item login: логин вашего аккаунта в GitHub
    \item id: транслитерация вашей фамилии. Например, ivanov.
    \item app: название выбранного приложения. Например, catty-reminders-app
\end{itemize}
Название pull request должно удовлетворять шаблону 63NN Регистрация Иванов И.И.

После создания pull request убедитесь что все проверки пройдены. Если проверки не пройдены - внесите изменения и переотройте
pull request чтобы проверка запустилась заново.

\section{Выполнение лабораторной работы}
Для выполнения лабораторной работы необходимо соблюдать следующую последовательность действий:

\begin{enumerate}
    \item При выполнении первой лабораторной работы создайте новую ветку \texttt{lab1} от существующей ветки, соответствующей названию выбранного приложения.
    \item Для каждой последующей лабораторной работы создавайте новую ветку от ветки предыдущей лабораторной работы. Например, ветка \texttt{lab2} создается от ветки \texttt{lab1} и т.д.
    \item Все файлы, необходимые для выполнения лабораторной работы, добавляйте в соответствующую рабочую ветку.
\end{enumerate}

\section{Процесс сдачи}
Для сдачи лабораторной работы Вам необходимо создать pull request в репозиторий \href{https://github.com/prafdin/devops-course-labs}{prafdin/devops-course-labs}
в ветку по названию выбранного приложения.

Перед созданием pull request убедитесь, что требуемый сценарий лабораторной работы может быть выполнен:
виртуальная машина включена, все необходимые приложения запущены.

Название pull request должно удовлетворять шаблону 63NN Лаб.1 Иванов И.И.

После создания pull request в вашем репозитории автоматически запустится набор \href{https://github.com/prafdin/check-assignment/tree/main/scripts}{проверок},
которые необходимо пройти.

В случае необходимости внесения изменений для успешного прохождения проверок:
\begin{itemize}
    \item внесите изменения в рабочую ветку;
    \item оставьте комментарий \texttt{/rerun-all} в pull request для повторного запуска проверок.
\end{itemize}

Если проверки упали по независящим от вас причинам, допускается их перезапуск без внесения изменений.
В случае, если вы считаете, что проверки упали неправомерно и все требования лабораторной работы выполнены, необходимо обратиться к преподавателю.

После успешного завершения всех проверок ожидайте проверку от преподавателя.

После внесения исправлений по замечаниям преподавателя необходимо запросить повторное ревью в pull request:

\begin{center}
    \includegraphics[width=0.5\textwidth]{media/re-request-review}
\end{center}
В рамках одной лабораторной работы допускается не более трёх запросов на повторное ревью.
При превышении указанного лимита при сдаче добавляются дополнительные вопросы в количестве, равном превышению.

После получения одобрения (approve) от преподавателя обучающийся допускается к посещению сдачи лабораторной работы.
На сдаче необходимо ответить на два вопроса по выполненной лабораторной работе, а также прокомментировать выполненную работу и пояснить принятые решения.

\subsection{Перезапуск автоматической проверки}

Если при создании pull request вы не учли все требования лабораторной работы или системы сдачи, проверку можно запустить
заново, добавив комментарий \texttt{/rerun-all} в pull request. При условии, что вы заранее зарегистрировались на курс,
система автоматически перезапустит проверки.

В ряде случаев, перечисленных ниже, команда \texttt{/rerun-all} может не сработать из-за особенностей работы GitHub Actions.
Тогда необходимо переоткрыть pull request: сначала закройте его, затем откройте снова.
Это действие инициирует повторную проверку с актуальными данными.

Ситуации, когда требуется переоткрыть pull request:
\begin{enumerate}
    \item переименование pull request;
    \item изменение кода GitHub Actions в ветке main основного репозитория.
\end{enumerate}
Список не является исчерпывающим. Если вы столкнулись с незадокументированным сценарием, при котором потребовалось
переоткрывать pull request, сообщите об этом в рамках программы Bug Bounty.

\section{Bug Bounty}
В рамках курса действует программа \textit{Bug Bounty}, направленная на выявление недочётов и ошибок в автоматических проверках лабораторных работ.

Если обучающийся обнаружил некорректную работу проверок (ошибки логики, ложные срабатывания, некорректные условия проверки и т.п.),
он может заявить о найденной проблеме и получить дополнительные преференции.

\subsection{Что считается недочётом проверки}

К недочётам автоматических проверок относятся:
\begin{itemize}
    \item ложные отрицательные срабатывания (проверка не проходит при корректно выполненной лабораторной работе);
    \item ложные положительные срабатывания (проверка проходит при некорректной реализации);
    \item некорректные или противоречивые требования проверки;
    \item ошибки в логике сценариев проверки;
\end{itemize}

\subsection{Неточности в руководстве и методических материалах}
В рамках программы также приветствуются вопросы, связанные с лабораторной работой. Если заданный вопрос помогает выявить
неточность, неоднозначность формулировок или запутанность руководства либо методических материалов, такая ситуация может
быть признана проблемой документации.

\subsection{Порядок сообщения о найденной проблеме}

Для того чтобы сообщить о найденной проблеме или задать вопрос, создайте Issue в исходном репозитории \href{https://github.com/prafdin/devops-course-labs}{prafdin/devops-course-labs}
с описанием ошибки.

\subsection{Преференции}
В случае подтверждения обнаруженной ошибки обучающемуся могут быть начислены бонусные баллы в диапазоне от 0.5 до 1.5 в зависимости от критичности ошибки.
За вопрос, позволивший выявить неточность документации, могут быть начислены бонусные баллы до 0.5.

Накопленные бонусные баллы можно использовать для закрытия лабораторных работ.
Любая лабораторная работа может быть закрыта при списании 3 баллов.
